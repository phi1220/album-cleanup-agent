# macOS workflow contract — 0.4

README documents setup and current behavior; this contract records the implementation boundaries. Runtime owners are native SwiftUI controls, `PhotoLibraryModel`, `ReviewMemory`, `PhotoImages`, and `VisionModel`.

| Source | UI consequence |
|---|---|
| 100 photos, one analysis action | Select up to 100 unprocessed authorized images in newest-first order, filtering completed advice before limiting; primary action processes all unprocessed photos. Internal batching of at most 12 images is invisible to selection; show true completed counts and stages. |
| model decides most outcomes | Clear keeps leave the pending list; cleanup with self-reported confidence >=0.90 routes to staging queue; uncertain or lower-confidence cleanup requires a decision. Favorites and keeper references are protected. Confidence is not a calibrated accuracy guarantee. |
| quick review and optional reason | Uncertainty sheet opens after analysis ends. Full-aspect preview, model reason, red labeled Delete and green labeled Keep, optional reason, next item on commit, and explicit skip/close. Keyboard shortcuts use Command to avoid conflicts with text entry. |
| restore or delete-all | Pending queue provides selection + restore with optional reason, per-photo modification, and an explicit delete-all button with consequence copy. This staging action never changes system Photos until delete-all. User requested one-click, so no extra checkbox/app confirmation; PhotoKit can request its own confirmation. |
| use feedback for future preferences | Only actual owner choices, restore actions, and successful final deletion become feedback. Persist choices and reasons atomically. Compress all distinct latest feedback into source-backed conditions and exceptions; no recency cutoff. Keep full raw evidence, validate coverage, and persist each completed compression batch. Photo analysis never starts or waits for compression/evolution; the explicit preference update action owns that work. Latest correction for a photo replaces its earlier example in the prompt. Model reasoning is labeled unconfirmed context, not owner policy. |
| compressed memory and Reef-based self-evolution | `PreferenceLearner` owns compression and a native prompt-evolution loop following Reef publication stages, without a Reef service dependency. Preference sheet shows summaries, evidence history, actual version metrics, update/cancel and rollback. Train/validation split is stable by photo/comparison group, without a capture-day threshold; validation uses fresh thumbnail replay with training-only memory. Enable only measured improvements; insufficient usable evidence and failed evaluation preserve the current policy. |
| Apple PhotoKit deleteAssets API and iCloud Photos support | Validate current asset snapshots, surviving keeper assets, access and delete capability. Submit one PhotoKit change; report success only from the callback. Do not retry deletion automatically. System deletion may sync across devices; restoration after actual deletion is through Photos Recently Deleted. |

## State and persistence

- One native window per process owns one observable model. Library tab shows only unanalyzed assets from the persisted current round. Uncertainty and queue tabs show applicable accessible saved assets, including older rounds. Completed retained photos stay out of the pending list. On refresh or after an operation, retain unfinished images and fill remaining slots from accessible unanalyzed images up to 100. Uncertain advice remains in its own tab and never blocks loading. Fewer than 100 is an actual accessible-unprocessed count, not a fixed current-round lock. Loading never starts a network request automatically.
- Results, staging choices and feedback persist at `~/Library/Application Support/AlbumCleanup/review-memory.json`; API keys stay in Keychain. A corrupt state file is not silently replaced. Save errors stop further mutations until resolved/restarted.
- `ReviewProtocol.batchRanges` balances each analysis input across paired concurrent slots: 100 photos normally produce ten batches of ten, with cuts adjusted around burst identifiers and adjacent capture times within 30 seconds. Metadata only guides grouping; each batch stays at most 12 images, maintains input order, and covers every input exactly once. Short rounds and retries use their actual unprocessed count; oversized bursts may be split, and comparison remains within each batch.
- Up to two batches run concurrently using a shared ephemeral network session. Each completed batch merges into the latest memory on the main actor and commits independently. Cancellation and fatal service/storage errors cancel in-flight batches and preserve committed results; Analyze All retries only unprocessed photos. Progress retains this attempt's completed/total counts alongside the current batch/stage; logs separate preview preparation and model request/save duration. PhotoKit network access is enabled for visible thumbnails, review and analysis. Show download progress, allow 120 seconds per image and cancel the native request on task cancellation/timeout. Failed items stay unanalyzed and retryable; model input remains a metadata-free 768px redraw. Grid and review provide explicit retry actions without changing system iCloud settings.
- Permission loss clears visible photos but retains local records; reauthorization revalidates snapshots and references. Changed/missing photos invalidate advice, not historical owner feedback.
- Restore means removal from the app staging queue. After system deletion, recovery belongs to system Photos; the app does not empty Recently Deleted.
- Deletion cancellation/failure creates no new owner cleanup feedback. Pending items remain for inspection. Successfully deleted photos are removed from active advice, while their owner feedback remains as history.
- Feedback records include source asset reference and snapshot locally, action, optional reason, timestamp and model observation. Raw asset IDs never enter model prompts. Clear feedback removes raw feedback, compressed memory and harness versions without undoing existing decisions. Same-photo corrections invalidate summaries and active harnesses that cite superseded sources; no-reason reconfirmation of the same choice preserves a previously entered owner reason.

- `PreferenceDigest` merges up to 128 new feedback items within an approximate 24,000-character input budget. Short wire references map back to immutable local UUID sources, with complete coverage and action consistency checks. Reasonless choices are immediately stored as local example IDs, with exact duplicate observations grouped by action for prompts; model compression handles explained feedback only. All source receipts remain, including reasonless examples. Every successful batch checkpoints atomically so interruption resumes from the last saved digest. Unchanged input makes no new compression request. Training-only memory is cached and checkpointed separately before candidate evaluation, and never seeded from all-feedback memory; replay failure does not force repeat compression. The explicit preference update action runs this work; analysis photos directly uses saved memory plus pending feedback. Compression/evolution failures do not prevent a later photo analysis.
- Training and validation use a stable photo/comparison-group split with no minimum capture-day requirement. Known keeper/candidate references stay in the same split. Old feedback falls back to existing comparison references or its asset ID, so capture dates are unnecessary. Deleted, changed or still-unavailable holdouts after attempted cloud retrieval are skipped before proposal; remaining usable holdouts must include retention and cleanup evidence to measure both safety and recall. Insufficient usable evidence preserves the strategy while retaining compressed preferences. No held-out label, reason, observation or asset ID enters candidate generation or paired replay. Same data/model is not reevaluated after success/rejection, including after rollback. Network/parse failures remain retryable. Endpoint/model changes ignore the old guidance.
- Candidate acceptance requires no extra unsafe cleanup, no worse unsafe/suggested ratio, no lost correct cleanup and strictly fewer edits; keeper references, favorites and confidence routing are included in scoring. A baseline with no suggested deletions has zero observed unsafe cleanup. Both labels and decisions use the same held-out set. The existing two-slot scheduler loads previews concurrently and evaluates paired current/candidate requests concurrently, without reducing coverage. Missing label classes stop before image retrieval. Progress reports completed operations; model response timings log counts/durations only. This is a single replay estimate; no significance or production gain claim. Known comparison groups do not detect every visually similar image across the library.

## Shared interaction and visual ownership

Native fields, segmented picker, sheets, scrollbars, focus and keyboard behavior are accepted. DESIGN.md owns colors and spacing; `DesignTokens` maps them into SwiftUI. Settings, review and restore share optional-reason semantics and inline error/status feedback. Red and green actions include labels/icons; all state is readable without color.

The status row stays outside the scrolling grid. Busy operations disable mutation actions; analysis can be cancelled. Library, uncertain and queue empty states are distinct. Queue selection is intersected with remaining IDs after updates. Review preview tasks are keyed by asset ID and ignore cancelled stale results. No deletion hotkey is the unmodified Enter or Delete key.

## Verification

`sh test-mac-review.sh` includes injected-model compression/paired-vision replay checks (75-source coverage, correction invalidation, migration, no held-out answer leakage, acceptance/rejection, no-repeat, missing previews, model changes and rollback), and checks model schema, confidence routing, keeper survival, edited/missing assets, 100-photo scope, metadata-free JPEG rendering, queue restoration, correction precedence, persisted round migration, filter-before-limit paging, unresolved items not blocking top-up, 19-to-100 top-up, duplicate suppression, final short/empty rounds, atomic state roundtrips, and the real batch scheduler's concurrency bound, out-of-order completion, fatal failure and cancellation. Injected PhotoKit callbacks verify enabled network options, progress, degraded/final and late callbacks, cloud/offline failure, timeout, cancellation and cancellation before starting, without reading or changing the library. The optional `--check-vision .env` uses only a generated test image. Python CLI tests remain independent. Actual library deletion is verified only through an explicit user action, never by a development test. Static audit/build do not substitute for interactive keyboard, layout or system-confirmation checks.
